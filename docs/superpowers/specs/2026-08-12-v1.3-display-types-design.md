## 1. 背景与决策上下文

### 1.1 起点

PRD §14.2 列出 v1.3 三种候选 displayType:`video-grid` / `timeline` / `comparison-table`。本设计文档定义它们的最终交付范围。

### 1.2 商业约束(决定设计的核心输入)

AnvilWiki 的商业模式是 **广告变现(Adsterra CPM/CPC)**。因此首页 explore 模块的价值不是「让用户在首页多停留」,而是 **「让用户从首页点进文章页,从而触发文章页广告曝光」**。这条逻辑链推翻了两个直觉上合理、实则损害收入的设计选择(见 §1.3)。

游戏 wiki 站的流量结构进一步放大了这个约束:约 70-80% 流量来自 Google 落地到具体文章页,首页流量占比小。因此首页模块的杠杆主要作用于「直接访问/忠实用户」,且这些用户的商业价值在于他们 **点击进入文章页** 的行为,而非首页停留本身。

### 1.3 第一性原理推翻的两个方案

| 原方案 | 推翻理由 |
|---|---|
| **video-grid = 首页直接 embed YouTube iframe** | 用户在你的站内看 YouTube 视频时,视频内嵌广告归 YouTube;看视频的 5 分钟里用户不滚动页面,你的 Adsterra 广告零曝光;视频结束用户大概率被 YouTube 推荐勾走跳出你的站。等于免费把 Google 来的流量送给 YouTube 变现。额外副作用:Lighthouse Performance 100 徽章不保。 |
| **comparison-table = columns 数组 + 行键值表格** | 对比表把信息完整呈现后,用户没有点进文章页的动力(信息已满足)。在广告变现模型下,「停留但不点击」的商业价值接近零。属于「为伪需求设计精巧数据结构」。 |

### 1.4 最终交付范围(方案 v3)

| displayType | 本次范围 | 商业逻辑 |
|---|---|---|
| **timeline** | ✅ 全力做 | 老玩家看版本日志 → 点进 patch notes 文章页 → 文章页广告曝光。零副作用。 |
| **video-grid** | ✅ 做组件,但 **缩略图卡片 + 跳转**(不 embed) | 视频入口在首页,点击跳到文章页。文章页里既有视频又有站内广告。同时保住 Lighthouse 100。 |
| **comparison-table** | ⏸ **本次不做**,PRD §14.2 标注「待真实需求验证」 | 广告变现 ROI 为负,推迟到有真实换皮用户反馈再做。 |

## 2. 架构

### 2.1 现有 dispatcher 模式(不动)

现有 `ExploreModules.astro` 是一个按 `displayType` 字段分发的容器组件,转发 `highlights` 数组给对应子组件。本次设计 **完全沿用此模式**,只追加 case 与子组件,不动现有 4 种的任何代码或数据。

```
src/components/home/
├── ExploreModules.astro        # dispatcher,本次加 2 个 case
└── modules/
    ├── CodeCards.astro         # 现有 — displayType: code-cards
    ├── StepByStep.astro        # 现有 — displayType: step-by-step
    ├── TierGrid.astro          # 现有 — displayType: tier-grid
    ├── CardList.astro          # 现有 — displayType: card-list
    ├── Timeline.astro          # 🆕 displayType: timeline
    └── VideoGrid.astro         # 🆕 displayType: video-grid
```

### 2.2 Props 类型策略:宽松(不动现有风格)

现有 `ExploreModules.astro` 的 `Props` 对 `displayType` 用 `string`、对 `highlights` 用统一的 `Array<{label, detail, badge?}>`。每个子组件内部各自定义自己的 `interface Props`。

**本次保持这个宽松风格,不引入 discriminated union。** 理由:

1. 一致性 — 与现有 4 个子组件的代码风格对齐,避免同一文件里两种风格共存。
2. JSON 不参与 TS 类型检查 — `import en from './en.json'` 默认是宽类型,在 .astro 里搞复杂泛型收不到类型安全的实际收益。
3. 类型安全的兜底靠 **schema 文档 + 构建时 Content schema 校验**,不靠 .astro 的 Props。

**代价**:JSON 写错了字段名 typecheck 不会报。这个代价 **在 §5 文档策略** 里通过「AI 可读的 JSDoc + 真实 demo 样本」缓解。

### 2.3 三层架构合规性检查

本设计严格符合 AGENTS.md 的三层分离原则:

- **框架层**(`src/components/`):新增 2 个子组件 + dispatcher 加 2 case。fork-once,游戏无关。
- **配置层**(`src/locales/<locale>.json`):新增 2 个 module 的 JSON 数据,换皮时改这里。
- **内容层**(`src/content/`):**不动**。

新增组件 **零游戏专属字符串**(所有文案来自 JSON),符合硬规则 1。

## 3. 组件设计

### 3.1 Timeline.astro

**用途**:展示版本更新日志、活动时间线、boss 发布顺序等具有时序性的内容。

**Schema**(放在 `home.explore.modules[i]`):

```json
{
  "order": 5,
  "name": "Update History",
  "description": "Major patches and events, newest first.",
  "href": "/updates",
  "displayType": "timeline",
  "highlights": [
    { "label": "v2.5", "detail": "New raid: Shadowforge released", "badge": "Latest" },
    { "label": "v2.4", "detail": "Rebalanced all S-tier weapons" },
    { "label": "v2.3", "detail": "Added 3 new bosses" }
  ]
}
```

**字段语义**(每个 displayType 必须在组件 JSDoc 里写清楚):

| 字段 | 类型 | 必填 | 语义 |
|---|---|---|---|
| `label` | string | ✅ | 时间点标识(版本号 `v2.5` / 日期 `2026-08-12` / 第几周 `Week 3`) |
| `detail` | string | ✅ | 该时间点的事件描述 |
| `badge` | string | ❌ | 可选徽章(如 `Latest` / `Hot` / `Ended`)。复用现有 CodeCards 的 badge 颜色规则:包含 `expire`/`ended` 显示红色,否则绿色。 |

**渲染规范**:

- 垂直时间轴。容器 `border-l-2 border-muted ml-3`,每项 `pl-4 relative`。
- 每项的圆点用绝对定位(`absolute left-[-9px] top-1`),尺寸 `h-3 w-3 rounded-full`。
- **首项(最新)圆点** 用主题色 `bg-nav`,**其余项** 用 `bg-muted` — 让「最新」视觉突出。这是唯一一处游戏无关的视觉差异,符合硬规则 2(只用 `var(--nav-theme)` 映射的 `bg-nav` token)。
- badge 复用 CodeCards 的两套颜色类(`bg-green-500/15` / `bg-red-500/15`)。**这是 badge 的特殊例外** — 见 §6.1 关于颜色规则的说明。
- 零 JS。

**Props interface**:

```typescript
interface Props {
  highlights: Array<{ label: string; detail: string; badge?: string }>;
}
```

### 3.2 VideoGrid.astro

**用途**:在首页提供视频入口,吸引用户点击进入文章页观看(文章页里有视频 + 站内广告)。

**关键决策**:首页 **不 embed YouTube iframe**,只渲染缩略图卡片。点击行为复用现有 ExploreModules 的「整卡可点击」机制 — 整个 module 卡片外层的 `<a>` 由 ExploreModules 提供,跳转到 module 的 `href`。**VideoGrid 组件本身不包含任何 `<a>` 标签**(避免与外层 `<a>` 嵌套,HTML 非法)。

> **设计选择**:不复用「每张缩略图独立 `<a>`」的模式。理由:
> 1. 现有 ExploreModules 结构是每个 module 整体外包 `<a>`(见代码),VideoGrid 若再加 `<a>` 会产生 `<a>` 嵌套,HTML 非法。
> 2. 本次 schema 不给每个视频单独 href(YAGNI,见 §11),所以每张缩略图独立可点的需求本就不存在。
> 3. 整块卡片一个链接跳到「视频列表文章页」与首页 explore 区其他模块的交互一致,用户预期统一。
>
> 未来若要支持「每视频独立 href」,需要 **统一改造 ExploreModules**(让所有 displayType 外层都不包 `<a>`,各自管理链接),不是仅改 VideoGrid。这个改造在本次范围外。

**Schema**:

```json
{
  "order": 6,
  "name": "Video Guides",
  "description": "Watch the best Anvil Quest walkthroughs.",
  "href": "/guides/video-walkthroughs",
  "displayType": "video-grid",
  "highlights": [
    { "title": "Beginner Guide", "youtubeId": "dQw4w9WgXcQ", "duration": "12:34" },
    { "title": "Boss Fight: Gelum", "youtubeId": "abc123xyz", "duration": "8:21" }
  ]
}
```

**字段语义**:

| 字段 | 类型 | 必填 | 语义 |
|---|---|---|---|
| `title` | string | ✅ | 视频标题。同时作为缩略图的 `alt` 文本(a11y)。 |
| `youtubeId` | string | ✅ | YouTube video id(11 位,如 `dQw4w9WgXcQ`)。组件据此 **自动** 拼接封面 URL `https://i.ytimg.com/vi/{youtubeId}/hqdefault.jpg`,用户无需单独提供缩略图。 |
| `duration` | string | ❌ | 视频时长(如 `12:34`)。渲染为缩略图右下角的 badge。 |

**渲染规范**:

- 网格布局:`grid gap-2 sm:grid-cols-2`(2 列,窄屏 1 列)。
- 每个卡片:`relative` 容器,内含 `<img>` 封面(16:9,`aspect-video object-cover`) + 右下角 duration badge(`absolute bottom-1 right-1 bg-black/80 text-white text-[10px] px-1.5 py-0.5 rounded`) + 底部标题区。
- 封面 `<img>` **必须** 带 `loading="lazy"` 和 `alt={title}`,并带 `width`/`height` 或用 `aspect-video` 约束以防止 CLS(Lighthouse CLS 指标)。
- 缩略图源 `https://i.ytimg.com/vi/{youtubeId}/hqdefault.jpg` 固定写死在组件里,不暴露给 JSON。
- **VideoGrid 组件不渲染任何 `<a>` 标签** — 点击行为由 ExploreModules 外层 `<a>` 提供。VideoGrid 只渲染缩略图 + 标题 + duration badge。

**Props interface**(与其他 5 种一致,只接收 highlights):

```typescript
interface Props {
  highlights: Array<{ title: string; youtubeId: string; duration?: string }>;
}
```

## 4. ExploreModules.astro 的集成改动

### 4.1 两种新 displayType 的集成方式完全一致

Timeline 和 VideoGrid 都遵循现有 4 种 displayType 的集成模式 — 由 ExploreModules 的外层 `<a>` 提供整卡点击行为,子组件只渲染内容:


无需传额外 prop,无需改造 ExploreModules 的外层结构。

### 4.2 ExploreModules.astro 的具体改动


3. 更新顶部 JSDoc 的「Supported displayTypes」列表,从 4 种扩到 6 种。

**不改**:外层 `<a>` 结构、`md:grid-cols-2` 布局、`localizePath` 逻辑、`View all` 底部链接、Props 类型。

### 4.3 Props 类型(不动)

`ExploreModules.astro` 的 `Props` 保持现状(见 §2.2)。`displayType: string` 的宽松类型自然容纳新值,无需扩 discriminated union。

## 5. AI 友好的文档策略(单一真相源)

### 5.1 不写独立的 docs/display-types.md

本次 **不新增** 独立的 displayType markdown 文档。理由:displayType 已有 3 处描述(PRD §6.5、组件 JSDoc、en.json demo 样本),新增第 4 处只会制造同步负担,违反「单一真相源」原则。

### 5.2 真相源:组件 JSDoc

每个 displayType 子组件的 `.astro` 文件顶部 JSDoc 是 **唯一定义字段语义的地方**。JSDoc 必须包含:

```typescript
/**
 * {displayType 名称} displayType — {一句话用途}.
 *
 * 何时使用:{典型场景,帮 AI/用户判断}
 *
 * highlights 字段:
 *   - label (string, 必填): {语义}
 *   - detail (string, 必填): {语义}
 *   - badge (string, 可选): {语义}
 *
 * JSON 示例(放在 home.explore.modules[]):
 *   {
 *     "displayType": "{name}",
 *     "highlights": [{ "label": "...", "detail": "..." }]
 *   }
 *
 * 渲染效果:{一句话视觉描述}
 */
```

**为什么这让 AI 能学到**:任何 AI 助手(Cursor / Copilot / Claude)读 `src/components/home/modules/` 时,直接从 JSDoc 拿到「何时用 + 字段含义 + 完整示例 + 视觉预期」四元组,这是 AI few-shot 学习的标准结构。JSDoc 紧贴代码,改组件时顺手改注释,同步成本最低。

### 5.3 PRD §6.5 同步更新

PRD §6.5 当前的「4 种 displayType」列表要更新为「6 种 displayType」,每种加一行简述(指向组件文件,不重复字段细节)。comparison-table 在 PRD §14.2 标注「待验证」。

### 5.4 demo 样本(en.json / ja.json)是最强学习材料

真实可运行的 JSON 样本(见 §6)是 AI 学习 displayType 最有效的形式 — 完整、上下文丰富、可直接复制修改。en.json 扩展到 6 个 module 后,7 种 displayType 里的 6 种都有了 demo 样本(comparison-table 除外)。

## 7. 颜色规则合规性

### 7.1 timeline 的时间轴圆点

用 `bg-nav` token(映射自 `var(--nav-theme)`)。符合硬规则 2(不用硬编码 hex)。

### 7.2 badge 颜色(已有例外)

timeline 的 badge 复用 CodeCards 的两套颜色(`bg-green-500/15 text-green-700` / `bg-red-500/15 text-red-700`)。**这是 AGENTS.md 硬规则 2 的已知例外** — Tailwind 颜色类用于 badge,因为 badge 表示状态(成功/警告),不表示主题色。这个例外在 CodeCards 已经存在并被接受,timeline 沿用同一规则,不引入新例外。

### 7.3 video-grid 的 duration badge

用 `bg-black/80 text-white`(纯黑半透明 + 白字)。这是 **视频时长的视觉惯例**(YouTube 本身就这么做),不是主题色,符合规则。video-grid 不引入新的颜色例外。

## 8. 测试与验证策略

### 8.1 不引入组件测试框架

现有测试只有 `tests/seo.test.ts` 和 `tests/url.test.ts`,无组件测试。本次 **不引入 Vitest + @testing-library/astro**,理由:

- 配置成本高,且 .astro 组件的 DOM 测试对静态站价值有限。
- 现有项目的测试文化是「关键 lib + SEO 逻辑测试」,不在 UI 组件层堆测试。

### 8.2 验证清单

| 验证项 | 命令 / 方式 | 通过标准 |
|---|---|---|
| TypeScript 类型 | `pnpm typecheck` | 0 error |
| 构建 | `pnpm build` | 成功,Content schema 校验通过 |
| SEO 测试 | `pnpm test` | 现有 seo.test.ts / url.test.ts 全绿 |
| sitemap 完整性 | 检查 `dist/sitemap-0.xml` | 不含 `/updates` 或 `/guides/video-walkthroughs`(因为无对应 MDX) |
